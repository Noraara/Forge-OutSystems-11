# Discover the actual target
Inspect environment, O11 vs ODC, app style, parent application, module membership, open module, existing edits, dependencies, theme/UI versions, roles and tool availability. Read project brief, design and latest relevant handoff.
Resolve ownership before creating/moving modules. Choose boundaries from responsibilities, reuse and dependencies, not a fixed module count. Verify the intended application contains the module and entry/home setup; never leave the user to discover an independent module after delivery.
Use live model/read tools for current state. Auto-merge is a user preference to inspect, not proof of success. Preserve concurrent user edits.
For a feature: actor/task/outcome, allowed records, valid input, transition rules, persistence, failure/retry and acceptance checks. Investigate risky integrations or offline/device requirements before committing design.
Use existing PRODUCT.md/DESIGN.md equivalents. O11 source may be remote, so a local companion project folder holds briefs and evidence; obtain its location from project context. Missing files do not make an existing app greenfield.
If user interaction is required, name the exact visible screen/control and expected result, based on current evidence. Distinguish platform developer account, Users administrator, application end-user, role and company membership. Do not guess role names or assign broad roles to bypass a defect.

When needed, use the [product brief](../assets/product-brief.md), [design specification](../assets/design-spec.md) and [feature plan](../assets/feature-plan.md). Reuse existing equivalents instead of creating duplicates.
